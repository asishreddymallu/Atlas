# Extending Atlas

Short recipes for the changes people most often want. Each recipe lists:
- the files to touch;
- the tests to add;
- the existing tests that pin today's state, and so will need a deliberate change.

The recipes were traced through the code on `final/submission`, and, where one exists, through the commit that last made the same kind of change. A recipe whose path could not be traced end to end says so.

Ground rules: [AGENTS.md](../AGENTS.md) and [CONTRIBUTING.md](../CONTRIBUTING.md). Run the suite serially (`ctest --test-dir build-tests --output-on-failure`).

## Add an instruction

**Verified against:**
- how the base RV64 W forms were made to assemble: commit `f43ed4f`, known_issues 109;
- how `mulw` flows through the code today.

**Not traced:** a new operand syntax (a new `SyntaxType` and its parser).

Files:
1. `src/common/instructions.h`: add the `Instruction` enum value (for example `kmulw`).
2. `src/common/instructions.cpp`. One instruction appears in several tables:
   - `instruction_encoding_map`: opcode, funct3, funct7;
   - `instruction_string_map`: name to enum;
   - `valid_instructions`, which the lexer uses to make it an `OPCODE`;
   - the format set it belongs to (`RTypeInstructions`, `ITypeInstructions`, ..., `MExtensionInstructions`, ...);
   - the per-format encoding map (for example `R_type_instruction_encoding_map`);
   - `instruction_syntax_map`, its operand forms. Without this row the parser rejects it (that was 109);
   - `disassemble()`, so the Output pane and the dumps name it.
3. **Execution.** Instructions are executed by their decoded fields, not their name:
   - `src/processor/alu.h` / `alu.cpp`: an `AluOp` and its operation, if no existing one fits;
   - `src/processor/rvss/rvss_control_unit.cpp` and `src/processor/rv5s/rv5s_control_unit.cpp`: map the opcode, funct3 and funct7 to that `AluOp`;
   - `src/processor/rvss/rvss_processor.cpp` and `src/processor/rv5s/rv5s_processor_base.cpp`: the execute and writeback switch on the opcode, if it is a new opcode group;
   - the hazard unit's read and write sets in `src/processor/rv5s/` (`rv5s_hdu.*`), if it reads or writes registers in a way no existing instruction does.
4. **Editor data:**
   - `resources/instructions/instructions.json`: the completion list;
   - `resources/instructions/instruction_docs.json`: format, summary and example.

Tests to add:
- Encoding and execution cases in the style of `test/w_forms_test.cpp`. Its tables are generated by `verification/tables/gen_w.py` from a spec-written ALU (`verification/lib/common.py`), never from the simulator.

Existing tests that pin today's state:
- `InstructionDocs.*` (`test/instruction_docs_test.cpp`) requires every assembler mnemonic to have a docs entry, and the support flag to match what the assembler does.
- `HazardTables.*` (`test/hazard_tables_test.cpp`) holds a generated per-mnemonic table. `verification/hazard/gen_tables.py` refuses to run while any assembler mnemonic lacks a spec row. So:
  1. add the row in `gen_tables.py`;
  2. regenerate;
  3. paste the new table into the test. **That is a change to an existing test.**
- `verification/`: the ISA sweep sweeps every mnemonic in the assembler's tables. Expect its program count, and so `verification/expected_summary.txt`, to change. Re-record it after reviewing the diff.

## Add a processor model

**Partly verified.** The engine side was traced through the h-nf model. The **processor dialog is three switches** (pipeline, hazard detection, forwarding; `src/processor/processor_choice.cpp`) that map onto exactly the five models. A sixth model needs a new way to choose it in `src/ui/dialogs/processor_dialog.*`, and that design was not traced.

Files:
1. `src/processor/processor_types.h`: add the `ProcessorType` value, before `ProcessorTypeCount`.
2. **The model:** a class beside `src/processor/rv5s/rv5s_processor_h_nf.{h,cpp}`, deriving from `RV5StageVM_Base` (`rv5s_processor_base.*`) or from `ProcessorBase`.
3. **Its diagram:**
   - a scene in `src/ui/processor_tab/processor_designs/` (see `rv5s_processor_h_nf_circuit_scene.h`), created in the model's constructor;
   - a layout JSON in `resources/circuit_designs/`, listed in `circuit_designs.qrc`.
4. `src/processor/processor_manager.cpp`:
   - `ProcessorFactory::RegisterVM<...>` in the constructor;
   - the model name and hazard flags in the metrics and metadata switches (search for `RV5Stage_H_NF`).
5. `src/processor/processor_choice.cpp`: `processorChoiceFor()` and `processorDescription()`, the status-bar name.
6. **Command line:** the `--vm` names in `cli/main.cpp` (`processorTypes`) and in `src/command_handler/command_handler.cpp` (the REPL's `load --vm`).
7. `src/scheduler_gate/reorder_gate.cpp`: decide whether Suggest reordering may run on it. Today only h-f and h-nf are allowed.

Tests to add:
- the model's own tests, like `test/rv5s_h_nf_test.cpp`;
- a wire-name gate entry (`test/wire_name_gate_test.cpp`).

Many suites are parameterised over an explicit list of the five models (`Models/...`, `Pipelines/...`). They do not pick up a new one by themselves: add it to the lists that should cover it.

## Add a cache replacement policy

### As a Lua script (no rebuild)

**Verified.** See [CUSTOM_REPLACEMENT_POLICY.md](CUSTOM_REPLACEMENT_POLICY.md) for the hooks:
- `chooseVictim`, required;
- `onAccess`, `onInsert`, `onEvict`, optional.

Steps:
1. Write the script beside `examples/custom-replacement-scripts/lru.lua`, `fifo.lua` and `lfu.lua`.
2. In the Cache tab, set Replacement Policy to **Custom** and choose the script. In code, call `Cache::loadCustomPolicyScript(path)`, then `reconfigure` with `ReplacementPolicy::Custom`.
3. Test it like `CacheLabLuaPolicy.ScriptMatchesBuiltIn` (`test/cache_lab_test.cpp`), which runs `lru.lua` and `fifo.lua` and requires exactly the built-in counts. `test/custom_policy_test.cpp` shows loading a script directly.

### As a built-in

**Verified** against how FIFO is wired.

Files:
1. `src/processor/cache/cacheconfig.h`: add the `ReplacementPolicy` value.
2. `src/processor/cache/policies/`: a class like `fifo.{h,cpp}` implementing `CacheReplacementPolicy` (`cache_replacement_policy.h`): `name()`, `type()`, `chooseVictim()`.
3. `src/processor/cache/cache.cpp`: a case in `createPolicy()`.
4. **The UI:**
   - `src/ui/cache_tab/cache_config_widget.ui`: an item in `repPolComboBox`;
   - `cache_config_widget.cpp`: a `tag(ui->repPolComboBox, ...)` line.

   The widget writes the combo by index (`setCurrentIndex(static_cast<int>(policy))`) and reads it by item data (known_issues 12). So keep the combo order equal to the enum order, or `Custom` will shift.
5. Wherever policies are named:
   - `src/cache_lab/lab_record_capture.cpp`: the lab record's `"lru"`/`"fifo"` names;
   - `src/ui/cache_tab/cache_set_model.cpp`: the live view's rank tooltip, which treats FIFO specially.

Tests to add:
- policy cases in `test/cache_policies_test.cpp`;
- if it should be checked independently, a policy in `verification/cache/cachemodel.py` plus a config in `verification/cache/oracle.py`. That changes the cache sweep's summary; re-record it.

## Add a Cache Lab preset

**Verified.**

Files:
1. `src/cache_lab/lab_presets.cpp`: one row in `labPresets()` with:
   - name;
   - exponents ("2^n Lines" sets the **number of sets**, known_issues 131);
   - write-hit and write-miss policies;

## Add a theme

### Built in

**Verified** against commit `42faf40` (six themes, T8).

Files:
1. `resources/themes/<name>.json`: copy an existing theme. `ThemeCatalogue.EveryThemeDefinesEveryToken` requires every token.
2. `resources/themes/themes.qrc`: list the file. `ThemeManager` loads every `*.json` under `:/themes`.
3. [THEMES.md](THEMES.md): how its colours were chosen, and its licence if it is a port.

Tests:
- `test/theme_catalogue_test.cpp` checks contrast (4.5:1 for main text; 3:1 for secondary text and control borders; 3:1 for the syntax colours of the ported themes), the timing-grid and diagram colours, and the dark-then-light order.
- `ThemeCatalogue.TenThemesShipWithTheApp` **pins the count at ten** and lists the ids. Adding a theme changes that test.

### Without a rebuild

Settings > Advanced Settings > **Install Theme...** copies a theme JSON into the user theme directory. That is `QStandardPaths::AppDataLocation` + `/themes` (`ThemeManager::installTheme`, `userThemesDirectory`). A user theme cannot replace a built-in id.

## Add a ribbon action

**Verified** against commit `ec675e4` (Suggest reordering).

Files:
1. `src/ui/main_window/main_window.{h,cpp}`: create the `QAction`, and give it an object name if tests should find it. Then add it to the page's group with:
   - `RibbonPage::addGroup` (`src/ui/ribbon/ribbon_page.h`);
   - `RibbonGroup::addLarge`, `addSmall` or `addSegmented` (`src/ui/ribbon/ribbon_group.h`).

   Mirror it in a menu if it belongs there.
2. **An icon:**
   - an SVG in `resources/icons/`, listed in `icons.qrc`;
   - an `Icon` value in `src/ui/theme/icon_manager.{h,cpp}`;
   - `setThemedIcon(action, Icon::...)`.

**The ribbon tests pin the layout.** `test/ribbon_navigation_test.cpp` lists:
- each page's groups (`kPageGroups`);
- every page button with its group and size (`kPageButtons`);
- the icon-less actions.

So a new group or button **must** be added to those lists: that is a deliberate change to an existing test, and it was the one change approved when Suggest reordering was added. Persistent groups (Run, File) are pinned the same way (`kPersistentButtons`).

Tests to add:
- the action's own behaviour, like `test/reorder_ui_test.cpp`, which triggers the action in the real window.

## Add a verification checker

**Verified** (the checkers in `verification/` were imported this way).

Files:
1. **The checker:** a script in a new or existing `verification/<area>/`. It must:
   - compute its expected values from a model written apart from the product;
   - print one summary line;
   - write generated files only under `verification/out/` (`verification/lib/vpaths.py`, `vpaths.out(...)`).
2. **If it must run simulator code:**
   - use an existing probe in `verification/probes/` (`atlas_verify_sweep run` prints the full final state);
   - or add one in `verification/probes/probes.cmake`, which is built only with `-DATLAS_BUILD_VERIFICATION=ON`;
   - in either case, run probes through `verification/lib/run_hermetic.sh`.
3. `scripts/run_verification.sh`: add a `step <name> '<summary regex>' <command>` line.
4. `verification/negative_controls.py`: add a control that plants one wrong value in a copy of the checker's output and requires exactly one more problem.
5. Run `scripts/run_verification.sh`. Review the new lines in `verification/out/summary.txt`. Record them with `--record`, and describe the checker in `verification/README.md`.
